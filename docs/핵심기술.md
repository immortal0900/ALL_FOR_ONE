# AI Agent & ReAct 패턴 핵심 기술 정리

---

## 1. LangGraph 기반 ReAct 패턴 AI Agent 아키텍처

### 선택 이유

| 기존 방식의 한계 | 해결 필요성 |
|-----------------|------------|
| 단순 LLM Chain은 한 번의 호출로 끝나 복잡한 분석 불가 | 부동산 분석은 입지/정책/시세 등 **다중 데이터 소스**를 순차적으로 조합해야 함 |
| 고정된 파이프라인은 데이터 부족 시 대응 불가 | Agent가 스스로 **도구 호출 여부를 판단**하고, 부족하면 재검색하는 동적 흐름 필요 |
| 일반 Agent는 상태 관리가 어려워 멀티스텝 추론 실패 | LangGraph의 **StateGraph**로 상태를 명시적으로 관리하여 복잡한 워크플로우 구현 |

### 구현 방법

- **구현 파일**: 
  - `src/agents/analysis/location_insight_agent.py`
  - `src/agents/analysis/nearby_market_agent.py`
  - `src/agents/analysis/policy_agent.py`

- **핵심 로직**:
  1. **StateGraph 정의**: 각 Agent별로 전용 State 클래스를 정의하여 입력/출력/중간 상태를 타입 안전하게 관리
  2. **Node 분리**: 데이터 수집(gemini_search, kakao_api_distance), 프롬프트 설정(analysis_setting), 추론(agent), 도구 실행(tools) 노드를 분리
  3. **Conditional Edge**: `router` 함수로 LLM 응답에 `tool_calls`가 있으면 도구 노드로, 없으면 종료로 분기
  4. **병렬 실행**: `nearby_market_agent`에서 kakao_api, real_estate_price, perplexity_search 노드를 병렬로 실행하여 응답 시간 단축

```
[ReAct 패턴 흐름]

START → 데이터수집(병렬) → 프롬프트설정 → Agent(LLM)
                                            ↓
                                    tool_calls 있음?
                                    ↓ Yes      ↓ No
                                  Tools     → END
                                    ↓
                                  Agent ←─┘ (반복)
```

- **참고 문서**: 
  - [LangGraph 공식 문서](https://langchain-ai.github.io/langgraph/)
  - [ReAct 논문](https://arxiv.org/abs/2210.03629)

### 핵심 기능

- Agent가 **자율적으로 도구 호출 여부를 판단**하여 필요한 정보만 수집
- 상태 기반 워크플로우로 **멀티스텝 추론**이 안정적으로 동작
- 노드 단위 분리로 **디버깅과 테스트가 용이**
- 병렬 노드 실행으로 **응답 시간 최적화**

## 2. YAML 기반 프롬프트 관리 시스템 (PromptManager)

### 선택 이유

| 기존 방식의 한계 | 해결 필요성 |
|-----------------|------------|
| 프롬프트를 Python 코드에 하드코딩하면 수정 시 배포 필요 | 프롬프트 변경만으로 Agent 동작을 조정하려면 **코드/프롬프트 분리** 필수 |
| 긴 프롬프트가 코드 가독성을 해침 | YAML 파일로 분리하여 **멀티라인 프롬프트**를 깔끔하게 관리 |
| 동일 프롬프트를 여러 곳에서 사용 시 중복 발생 | **PromptType Enum**으로 중앙 집중 관리하여 일관성 보장 |
| 세그먼트별 다른 프롬프트 적용이 복잡함 | `segment_directive()` 함수로 **세그먼트 번호에 따라 동적 로딩** |

### 세그먼트 분리 설계 이유

| 문제점 | 세그먼트 분리로 해결 |
|-------|-------------------|
| **Context Window 한계**: 전체 보고서(6페이지)를 한 번에 생성하면 토큰 제한 초과 또는 품질 저하 | 4개 세그먼트로 분할하여 **각 세그먼트당 1,500~4,000자**씩 안정적 생성 |
| **품질 집중**: LLM이 한 번에 너무 많은 내용을 생성하면 후반부 품질 저하 | 세그먼트별로 **전문화된 프롬프트** 적용하여 각 섹션 품질 보장 |
| **맥락 유지**: 긴 보고서에서 앞부분 내용을 뒷부분에서 참조해야 함 | `prev_segment_context()` 함수로 **이전 세그먼트 요약**을 다음 세그먼트에 전달 |
| **디버깅 용이성**: 전체 보고서 오류 시 원인 파악 어려움 | 세그먼트 단위로 **개별 검증 및 재생성** 가능 |

#### 세그먼트 구성

| 세그먼트 | 페이지 | 내용 | 프롬프트 |
|---------|-------|------|---------|
| **SEGMENT_01** | 1~2 | 사업환경 분석 (입지분석, 개발호재) | `JUNG_MIN_JAE_SEGMENT_01` |
| **SEGMENT_02** | 3~4 | 정책 환경 분석 (policy_agent 결과 그대로 사용) | `JUNG_MIN_JAE_SEGMENT_02` |
| **SEGMENT_03** | 5~6 | 수요타겟 분석 (공급/수요, 미분양, 인구) | `JUNG_MIN_JAE_SEGMENT_03` |
| **SEGMENT_04** | 7~8 | 인근 매매/분양 비교 + 종합결론 (SWOT, 요인분석, 분양가) | `JUNG_MIN_JAE_SEGMENT_04` |

### LLM 호출 횟수 분석

**jung_min_jae_agent 1회 실행 시 LLM 호출 횟수: 최소 7회 ~ 최대 8회**

| 단계 | LLM 호출 | 용도 | 모델 |
|-----|---------|------|------|
| **1. SEGMENT_01 생성** | 1회 | 사업환경 분석 보고서 생성 | `report_llm` (GPT-4o) |
| **2. SEGMENT_02 생성** | 1회 | 정책 환경 분석 보고서 생성 | `report_llm` (GPT-4o) |
| **3. SEGMENT_03 생성** | 1회 | 수요타겟 분석 보고서 생성 | `report_llm` (GPT-4o) |
| **4. SEGMENT_04 생성** | 1회 | 종합결론 보고서 생성 | `report_llm` (GPT-4o) |
| **5. 이전 세그먼트 요약** | 3회 | seg2, seg3, seg4 생성 전 이전 내용 요약 | `dev_llm` (GPT-4o-mini) |
| **6. Reflection (성찰)** | 1회 | think_tool 호출하여 자체 검증 | `dev_llm` + think_tool |
| **7. 피드백 반영** | 0~1회 | 피드백이 있을 경우에만 수정 | `report_llm` (GPT-4o) |

### LLM 호출 방식: State 공유 + 독립 호출

**각 LLM 호출은 State만 공유하고, 대화 히스토리(Memory)를 공유하지 않습니다.**

| 구분 | 공유 여부 | 설명 |
|-----|----------|------|
| **State (상태)** | O 공유 | `segment_buffers`, `messages`, `final_draft` 등 StateGraph의 상태값 |
| **대화 히스토리** | X 미공유 | 각 호출은 새로운 대화로 시작, 이전 LLM 응답을 기억하지 않음 |
| **프롬프트 컨텍스트** | 부분 공유 | `prev_segment_context()`로 이전 세그먼트 **요약**만 전달 (원문 전체 X) |

```
[State 공유 + 독립 호출 구조]

┌─────────────────────────────────────────────────────────────────────┐
│                      JungMinJaeState (공유 상태)                      │
│  ┌─────────────────┬─────────────────┬─────────────────────────┐   │
│  │ segment_buffers │    messages     │   start_input, etc.     │   │
│  │ {seg1: "...",   │ [SystemMsg,     │ {target_area: "...",    │   │
│  │  seg2: "...",   │  HumanMsg, ...] │  main_type: "...", ...} │   │
│  │  seg3: "...",   │                 │                         │   │
│  │  seg4: "..."}   │                 │                         │   │
│  └─────────────────┴─────────────────┴─────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────┘
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
          ▼                   ▼                   ▼
   ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
   │  LLM 호출 1  │     │  LLM 호출 2  │     │  LLM 호출 N  │
   │ (seg1 생성)  │     │ (seg2 생성)  │     │ (reflection) │
   │             │     │             │     │             │
   │ [새 대화]    │     │ [새 대화]    │     │ [새 대화]    │
   │ - SystemMsg │     │ - SystemMsg │     │ - SystemMsg │
   │ - HumanMsg  │     │ - HumanMsg  │     │ - HumanMsg  │
   │   (seg1     │     │   (seg2     │     │   (draft +  │
   │   프롬프트)  │     │   프롬프트 + │     │   체크리스트)│
   │             │     │   seg1 요약) │     │             │
   └─────────────┘     └─────────────┘     └─────────────┘
          │                   │                   │
          ▼                   ▼                   ▼
   State에 저장         State에 저장         State에 저장
   (seg1 → buffers)   (seg2 → buffers)   (feedback → state)
```

#### 왜 대화 히스토리를 공유하지 않는가?

| 이유 | 설명 |
|-----|------|
| **토큰 효율성** | 전체 대화 히스토리를 매번 전달하면 토큰 비용 급증 (보고서 4개 = 수만 토큰) |
| **컨텍스트 윈도우 한계** | GPT-4o의 128K 토큰 내에서도 긴 히스토리는 품질 저하 유발 |
| **독립적 품질 보장** | 각 세그먼트가 **전문화된 프롬프트**로 독립 생성되어 품질 일관성 확보 |
| **맥락은 요약으로 충분** | `prev_segment_context()`가 이전 내용을 **핵심만 요약**하여 전달 |

#### 맥락 전달 방식: 원문 vs 요약

```python
# 원문 전체 전달 (X - 비효율적)
# messages = [이전 seg1 전체, 이전 seg2 전체, 현재 seg3 프롬프트]  
# → 토큰 폭발, 품질 저하

# 요약 전달 (O - 효율적)
def prev_segment_context(state):
    segments = list(state.get(segment_buffers_key, {}).values())
    summary = dev_llm.invoke([
        SystemMessage(content=summary_prompt),  # "핵심만 요약하라"
        HumanMessage(content=str(segments))
    ])
    return f"# 이전 세그먼트 요약\n{summary.content}"
    # → 이전 seg1, seg2의 핵심만 200~500토큰으로 압축
```

```
[LLM 호출 흐름]

seg=1 → agent(LLM 1회) → seg=2 → prev_segment_context(LLM 1회) → agent(LLM 1회)
                                         ↓
seg=3 → prev_segment_context(LLM 1회) → agent(LLM 1회)
                                         ↓
seg=4 → prev_segment_context(LLM 1회) → agent(LLM 1회)
                                         ↓
finalize_merge → reflection_prompt → reflect_agent(LLM 1회, think_tool)
                                         ↓
                              apply_reflection(LLM 0~1회)
                                         ↓
                                        END

총 LLM 호출: 7~8회 (각 호출은 독립적, State만 공유)
```

- **구현 파일**:

  - `src/prompts/PromptType.py` (Enum 정의)

- **핵심 로직**:
  1. **PromptType Enum**: 프롬프트 이름, YAML 경로, 설명을 하나의 Enum 멤버로 관리
  2. **YAML 파싱**: `yaml.safe_load()`로 파일을 읽고, 각 키를 PromptTemplate 객체로 변환
  3. **변수 치환**: `get_prompt(**kwargs)` 메서드로 `{target_area}`, `{date}` 등 플레이스홀더를 런타임 값으로 치환
  4. **세그먼트별 분기**: `segment_directive(seg)` 함수가 세그먼트 번호에 따라 SEGMENT_01~04 프롬프트를 동적으로 반환

```python
# src/agents/jung_min_jae/jung_min_jae_agent.py (lines 68-75)
def segment_directive(seg: int) -> str:
    if seg == 1:
        return PromptManager(PromptType.JUNG_MIN_JAE_SEGMENT_01).get_prompt()
    if seg == 2:
        return PromptManager(PromptType.JUNG_MIN_JAE_SEGMENT_02).get_prompt()
    if seg == 3:
        return PromptManager(PromptType.JUNG_MIN_JAE_SEGMENT_03).get_prompt()
    return PromptManager(PromptType.JUNG_MIN_JAE_SEGMENT_04).get_prompt()

# src/agents/jung_min_jae/jung_min_jae_agent.py (lines 78-89)
def prev_segment_context(state: JungMinJaeState) -> str | None:
    seg = state.get(segment_key, 1)
    if seg <= 1:
        return None  # 첫 세그먼트는 이전 맥락 없음
    
    summary_prompt = PromptManager(PromptType.JUNG_MIN_JAE_SUMMARY).get_prompt()
    buffers = state.get(segment_buffers_key, {})
    segments = list(buffers.values())
    response = LLMProfile.dev_llm().invoke(  # 요약용 LLM 호출
        [SystemMessage(content=summary_prompt), HumanMessage(content=str(segments))]
    )
    return f"# 이전 세그먼트 요약/맥락\n{response.content}"
```

## 3. 하이브리드 검색(Hybrid Search) RAG 시스템

### 선택 이유

| 기존 방식의 한계 | 해결 필요성 |
|-----------------|------------|
| **순수 벡터 검색**은 "LTV 70%"같은 정확한 수치 매칭에 약함 | 정책 문서에서 **정확한 규제 수치**를 찾으려면 키워드 매칭 필수 |
| **순수 키워드 검색**은 "대출 규제 강화"와 "주담대 한도 축소"를 연결 못함 | **의미적 유사성**을 파악하여 동의어/유사 표현 검색 필요 |
| 두 방식을 단순 병합하면 중복 결과 발생 | **가중치 기반 스코어 병합**으로 두 방식의 장점만 결합 |

### 구현 방법

- **구현 파일**: 
  - `src/tools/rag/retriever/policy_pdf_retriever.py` (PolicyPDFRetriever 클래스)
  - `src/tools/rag/document_loader/policy_pdf_loader.py` (PolicyPDFLoader 클래스)
  - `src/tools/rag/chunker/default_chunker.py` (RecursiveCharacterTextSplitter)

- **핵심 로직**:
  1. **문서 로딩**: `PolicyPDFLoader`가 PDF에서 텍스트 추출 + 정책 유형/날짜/제목 메타데이터 자동 추출
  2. **청킹**: `RecursiveCharacterTextSplitter`로 1500자 단위 분할 (150자 오버랩)
  3. **벡터 저장**: PGVector(Supabase)에 OpenAI Embedding과 함께 저장
  4. **하이브리드 검색**:
     - `semantic_search()`: 벡터 유사도 기반 검색
     - `keyword_search()`: 문서 내 키워드 빈도(TF) 기반 검색
     - `hybrid_search()`: 두 결과를 **가중치(기본 0.7:0.3)**로 병합

```python
# src/tools/rag/retriever/policy_pdf_retriever.py (lines 126-200)
def hybrid_search(self, query, keywords=None, semantic_weight=0.7, k=5):
    # 1. 의미 검색 (벡터 유사도)
    semantic_results = self.semantic_search(query, k=k*2)
    
    # 2. 키워드 추출 (쿼리에서 LTV, DSR 등 중요 용어 자동 추출)
    if keywords is None:
        keywords = self._extract_keywords(query)
    
    # 3. 키워드 검색 (TF 빈도)
    keyword_results = self.keyword_search(keywords, k=k*2)
    
    # 4. 스코어 병합 (순위 기반 점수 + 가중치 적용)
    combined_scores = {}
    for idx, doc in enumerate(semantic_results):
        rank_score = (len(semantic_results) - idx) / len(semantic_results)
        combined_scores[doc_id] = semantic_weight * rank_score
    
    for idx, doc in enumerate(keyword_results):
        keyword_score = (1 - semantic_weight) * (1 - idx / len(keyword_results))
        combined_scores[doc_id] += keyword_score  # 기존 점수에 추가
    
    return sorted_by_score[:k]
```

## 7. Langfuse 이중 계층 Observability

### 선택 이유

| 기존 방식의 한계 | 해결 필요성 |
|-----------------|------------|
| LLM 호출 비용을 수동으로 추적하면 누락 발생 | 모든 LLM 호출의 토큰/비용을 **자동으로 추적**하여 비용 최적화 |
| LangChain 자동 추적은 SDK 직접 호출(Gemini, Perplexity)을 감지 못함 | **이중 계층 추적**으로 LangChain 경유 + SDK 직접 호출 모두 커버 |
| 1회 요청에 30개+ LLM 호출이 발생하는데, 개별 트레이스로 흩어지면 전후 비교 불가 | **세션 ID로 묶어** 1회 요청의 전체 LLM 호출을 한 화면에서 확인 → 변경 전/후 비교 용이 |
| Observability 도입 시 기존 코드 수정 필요 | **Graceful Degradation**: `LANGFUSE_ENABLED=false`면 모든 메서드가 안전한 기본값 반환 |

### 구현 방법

- **구현 파일**:
  - `src/utils/langfuse_tracker.py` (TokenTracker 싱글톤, 404줄)
  - `src/utils/llm.py` (RetryableChatOpenAI, `_merge_langfuse_config()`)
  - `src/tools/gemini_search_tool.py` (`@observe` + `update_observation`)
  - `src/tools/perplexity_search_tool.py` (`@observe` + `update_observation`)

- **핵심 로직 — 이중 계층 아키텍처**:

  이 프로젝트의 LLM 호출은 두 경로로 나뉩니다:
  - **LangChain 경유 호출** (OpenAI/Claude): LangChain의 `ChatOpenAI`를 통해 호출 → LangChain이 자동으로 토큰/비용 기록
  - **SDK 직접 호출** (Gemini/Perplexity): 각 회사의 공식 SDK를 직접 사용 → LangChain이 감지 못함 → 수동으로 기록 필요

```
[이중 계층 추적 구조]

계층 1: LangChain 자동 추적 (OpenAI, Claude)
├─ RetryableChatOpenAI가 LLM을 호출할 때마다
│  _merge_langfuse_config()가 "추적 리스너(CallbackHandler)"를 자동 끼워넣음
│  → LLM 호출 시작/종료 시 리스너가 토큰 수와 비용을 Langfuse로 전송
│
│  [핵심] 기존에 등록된 다른 리스너가 있으면 덮어쓰지 않고 "목록에 추가"
│  → LangGraph의 ToolNode가 자체 리스너를 등록하는데, 이를 보존해야 Agent가 정상 동작
└─ 28개 LLM 호출 지점이 코드 수정 없이 자동 추적

계층 2: SDK 직접 호출 추적 (Gemini, Perplexity)
├─ Gemini (google-genai SDK), Perplexity (openai SDK)는
│  LangChain을 거치지 않아 자동 추적이 불가능
│
├─ @observe 데코레이터: Langfuse SDK가 제공하는 함수 래퍼.
│  함수 진입/종료를 자동으로 감지하여 "이 함수가 실행됐다"는 기록(Span)을 생성.
│  as_type="generation"으로 설정하면 LLM 호출 전용 Span이 되어
│  토큰 수/비용/모델명 등 LLM 특화 필드를 기록할 수 있음.
│
├─ update_observation(): @observe가 만든 Span에 추가 정보(토큰 수, 비용, 출력)를 기록
└─ Langfuse 비활성화 시 → @observe가 아무것도 하지 않는 빈 데코레이터로 변환 (no-op)
```

  ```python

  @asynccontextmanager

          _active_session_id.reset(token)

  # 사용 예시 (main_api.py)
  async with tracker.session_context(session_id=job_id):
      result = await graph.ainvoke(...)
      # 이 안에서 발생하는 모든 LLM 호출이 job_id 세션에 자동 귀속
  ```

- **핵심 로직 — Graceful Degradation 패턴**:

  `LANGFUSE_ENABLED=false`이거나 langfuse 패키지가 미설치된 환경에서도 기존 시스템은 정상 동작합니다:

  | 메서드 | 비활성화 시 반환값 | 활성화 시 반환값 |
  |-------|-----------------|---------------|
  | `get_callback_handler()` | `None` | `CallbackHandler()` |
  | `get_langfuse_config()` | `{}` | `{"callbacks": [handler], ...}` |
  | `merge_config()` | 기존 config 그대로 | handler 병합된 config |
  | `observe()` | identity decorator (no-op) | Langfuse `@observe` |
  | `session_context()` | 즉시 yield | ContextVar 설정 + 전파 |

- **참고 문서**:
  - [Langfuse 공식 문서](https://langfuse.com/docs)
  - [Langfuse LangChain 통합](https://langfuse.com/docs/integrations/langchain/tracing)

### 핵심 기능

## 8. DeepEval Two-Tier 테스트 아키텍처

### 선택 이유

| 기존 방식의 한계 | 해결 필요성 |
|-----------------|------------|
| LLM 출력은 비결정적이라 단위 테스트로 품질 검증 불가 | **LLM-as-Judge** 방식으로 출력 품질을 정량 평가 |
| DeepEval 기본 메트릭은 범용적 → 부동산 분석 보고서 품질 측정에 부적합 | 도메인 특화 **자체 커스텀 메트릭** 설계 (AnalysisDepth, DataFidelity 등) + 에이전트별 **가중치 오버라이드** |

## 9. Structured Output 스키마 시스템

### 선택 이유

| 기존 방식의 한계 | 해결 필요성 |
|-----------------|------------|
| LLM이 자유 텍스트(마크다운+설명)를 반환하면 `json.loads()` 실패 | **API 레벨에서 JSON 스키마를 강제**하여 파싱 실패율 0% |
| 각 API(Gemini, Perplexity)마다 스키마 적용 방식이 다름 | **중앙 스키마 저장소**에서 Pydantic 모델 → API별 형식으로 자동 변환 |
| Text-to-SQL에서 LLM이 `SELECT *`, 한글 alias(`AS "연도"`), 마크다운 코드 펜스 등 예측 불가능한 SQL 생성 → downstream `KeyError` | **시스템 프롬프트 규칙(1차) + StructuredOutput(2차)** 이중 방어 |
| 후처리 파싱 코드가 20줄+ → 에러 처리 복잡 | 스키마 강제로 후처리를 `json.loads()` 1줄로 축소 |

### 구현 방법

- **구현 파일**:
  - `src/agents/state/structured_schemas.py` (9개 Pydantic 스키마, 193줄)
  - `src/tools/gemini_search_tool.py` (`response_json_schema` 적용)
  - `src/tools/perplexity_search_tool.py` (`response_format.json_schema` 적용)
  - `src/tools/kostat_api.py` (`.with_structured_output(MovePopulationQuery)`)

- **핵심 로직 — API별 적용 방식**:

  각 LLM API는 JSON 스키마를 강제하는 방식이 다릅니다. Pydantic의 `.model_json_schema()` 메서드로 JSON Schema dict를 생성한 뒤, 각 API의 형식에 맞게 전달합니다:

  ```python
  # Gemini: response_mime_type + response_json_schema
  # src/tools/gemini_search_tool.py (lines 82-91)
  generation_config = {
      "response_mime_type": "application/json",
      "response_json_schema": NearbyMarketGeminiSchema.model_json_schema(),
  }
  response = client.models.generate_content(
      model="gemini-2.5-pro", contents=prompt, config=generation_config
  )

  # Perplexity: response_format (OpenAI 호환)
  # src/tools/perplexity_search_tool.py (lines 56-60)
  kwargs["response_format"] = {
      "type": "json_schema",
      "json_schema": {"schema": NearbyMarketPerplexitySchema.model_json_schema()},
  }
  response = client.chat.completions.create(**kwargs)
  ```

- **핵심 로직 — Text-to-SQL 이중 방어 (시스템 프롬프트 + StructuredOutput)**:

  LLM에게 SQL을 생성하게 할 때, 프롬프트 지시만으로는 `SELECT *`, 한글 alias, 마크다운 코드 펜스 등 예측 불가능한 변형이 발생합니다.

  `.with_structured_output(MovePopulationQuery)`는 LLM이 `{"sql": "SELECT ..."}` 형태의 **JSON으로** 응답하도록 강제합니다. SQL 자체를 검증하는 것이 아니라, SQL을 JSON 필드 안에 넣게 하여 마크다운 코드 펜스(`\`\`\`sql...`)나 설명 텍스트("아래는 SQL입니다...")가 섞이는 것을 원천 차단합니다. 추가로 Field의 `description`이 LLM에게 "어떤 컬럼을 사용해야 하는지" 지시하는 역할을 합니다:

  ```python
  # src/tools/kostat_api.py — 수정 전 (StrOutputParser)
  chain = prompt | LLMProfile.dev_llm() | StrOutputParser()
  query = chain.invoke({"question": question})
  # LLM이 "```sql\nSELECT * FROM ...\n```" 같은 변형 SQL 생성 → KeyError

  # 수정 후 (StructuredOutput으로 형식 강제)
  from agents.state.structured_schemas import MovePopulationQuery
  llm = LLMProfile.dev_llm().with_structured_output(MovePopulationQuery)
  response = llm.invoke(prompt.format_messages(question=new_question))
  query = response.sql  # JSON의 sql 필드 → 순수 SQL 문자열만 반환
  ```

  ```python
  # MovePopulationQuery 스키마 — Field description이 LLM에게 컬럼 지시 역할
  class MovePopulationQuery(BaseModel):
      sql: str = Field(
          description=(
              "SELECT year, origin, destination, total FROM age_population WHERE ... "
              "형태의 PostgreSQL 쿼리. "
              "반드시 year, origin, destination, total 4개 컬럼만 SELECT하세요. "
              "id 컬럼과 컬럼 alias(AS)는 사용하지 마세요."
          )
      )
  ```

  | 방어선 | 역할 | 한계 |
  |--------|------|------|
  | 1차: 시스템 프롬프트 규칙 | LLM이 올바른 컬럼을 **의도적으로** 사용하도록 유도 | LLM이 지시를 무시할 수 있음 |
  | 2차: StructuredOutput 스키마 | 출력을 **JSON 형식으로 강제** (마크다운/설명 텍스트 불가) + Field description으로 컬럼명 지시 | SQL 문법 자체의 정확성은 검증 불가 |

  두 방어선이 결합되어야 **"올바른 컬럼 + 순수 SQL 문자열"** 양쪽이 보장됩니다.

- **스키마 목록**:

  | 스키마 | 사용 에이전트 | 대상 API | 용도 |
  |-------|-------------|---------|------|
  | `NearbyMarketGeminiSchema` | 주변시장 | Gemini | 매매 3 + 분양 3 아파트 JSON 강제 |
  | `LocationInsightGeminiSchema` | 입지분석 | Gemini | 지역특징 + 호재 리스트 JSON |
  | `NearbyMarketPerplexitySchema` | 주변시장 | Perplexity | 분양아파트 검증 JSON |
  | `CompetitionItem` / `PrePromiseCompetitionResult` | 공급/수요 | Tavily+LLM | 청약경쟁률 파싱 |
  | `HousingRuleItem` / `HousingRuleList` | 청약FAQ | LLM | 주택공급규칙 요약 |
  | `MovePopulationQuery` | 인구분석 | `.with_structured_output()` | SQL을 JSON 필드로 감싸 원본 컬럼명 강제 |

- **참고 문서**:
  - [Pydantic 공식 문서](https://docs.pydantic.dev/)
  - [Gemini Structured Output](https://ai.google.dev/gemini-api/docs/structured-output)

### 핵심 기능

- **API 레벨 JSON 강제**: Gemini(`response_json_schema`) + Perplexity(`json_schema`) + LangChain(`.with_structured_output()`) 모두 지원
- **Text-to-SQL 이중 방어**: 시스템 프롬프트(원본 컬럼명 지시) + StructuredOutput(SQL을 JSON 필드로 감싸 마크다운/설명 텍스트 원천 차단)
- **중앙 스키마 저장소**: 모든 스키마를 `structured_schemas.py` 한 파일에서 관리
- **Pydantic Field description**: 스키마 필드의 description이 LLM에게 추가 지시 역할 (어떤 컬럼을 사용해야 하는지)
- **후처리 코드 최소화**: 20줄+ 파싱 로직 → `json.loads()` 1줄

  - `src/tools/rag/vector_store.py` (engine_args: pool_pre_ping, pool_recycle)

- **핵심 로직 — 이중 Retry 제거**:

  ```python
  # src/utils/llm.py
  class RetryableChatOpenAI(ChatOpenAI):
      max_retries: int = 0  # SDK 내부 retry 비활성화 (자체 retry만 사용)

      def _get_total_timeout(self) -> float:
          """전체 retry 루프 시간 제한 = request_timeout x 2"""
          return (self.request_timeout or 300) * 2

      def invoke(self, input, config=None, **kwargs):
          total_timeout = self._get_total_timeout()
          start_time = time.monotonic()
          for i in range(5):
              if time.monotonic() - start_time > total_timeout:
                  raise TimeoutError(f"전체 재시도 시간 제한 초과 ({total_timeout:.0f}초)")
              # ... retry 로직 ...
  ```

- **핵심 로직 — 조건부 컨텍스트 주입 (토큰 폭발 방지)**:

  ```
  [토큰 누적 방지]
  Before: seg=1(7만) → seg=2(14만) → seg=3(21만) → seg=4(28만) → ContextOverflow!
  After:  seg=1(7만, 전체 기초자료) → seg=2~4(지시서만, ~2만) → 최대 8만 토큰
  ```

  LLM의 Attention 메커니즘은 이전 메시지를 기억하므로, seg>=2부터는 기초자료를 다시 주입할 필요 없이 짧은 지시서만 추가하면 됩니다.

- **핵심 로직 — E2E 폴링 최적화**:

  파이프라인 완료까지 27~55분 소요됩니다. 5초마다 "끝났나?" 확인하면 40분 동안 480회 불필요한 HTTP 요청이 발생합니다. 30초 간격으로 변경하여 80회로 줄이고(네트워크 부하 83% 감소), 타임아웃도 실제 소요 시간보다 짧은 10분에서 2시간으로 정상화하여 거짓 실패를 방지합니다.

### 핵심 기능

- **이중 Retry 제거**: SDK 내부 retry 비활성화(`max_retries=0`) + 외부 retry에 전체 시간 제한
- **조건부 컨텍스트 주입**: seg==1에서만 전체 기초자료 주입, seg>=2는 지시서만 → 28만 → 8만 토큰
- **Docker 패키지 최적화**: 불필요 19개 패키지 제거 (torch ~800MB, docling ~200MB 등)
- **E2E 폴링 최적화**: 5초 → 30초 간격 (80회), 타임아웃 10분 → 2시간
- **DB 커넥션 풀 설정**: `pool_pre_ping=True` + `pool_recycle=600` → Supabase idle timeout 대응

## 11. PDF 적응형 테이블 렌더링

### 선택 이유

| 기존 방식의 한계 | 해결 필요성 |
|-----------------|------------|
| WeasyPrint으로 PDF 생성 시 모든 표에 동일한 CSS 적용 → 11~12컬럼 표가 A4 유효 폭(170mm)을 초과하여 오른쪽 열 잘림 | 컬럼 수에 따라 **넓은 표만 선별**하여 축소 렌더링, 다른 표는 무영향 |
| CSS 자체는 "컬럼 수가 N개 이상이면" 같은 조건 분기를 지원하지 않음 | HTML 변환 후 **Python으로 DOM을 분석**하여 CSS 클래스를 동적 부여하는 **Hybrid 방식** |
| LLM이 생성하는 Markdown 표 앞에 빈 줄이 없으면 python-markdown이 `<table>`로 파싱 못함 | 전처리 단계에서 **빈 줄 강제 삽입** → 안정적 HTML 변환 보장 |

### 구현 방법

- **구현 파일**: `src/tools/send_gmail.py`
  - `_strip_outer_fence()` (lines 109~128): LLM 출력의 ``` 껍데기 제거
  - `_ensure_blank_line_before_tables()` (lines 82~106): 표 앞 빈 줄 강제 삽입
  - `_classify_wide_tables()` (lines 137~157): 8+컬럼 표에 `class="wide-table"` 부여
  - `markdown_to_pdf()` (lines 163~260): 전체 파이프라인 오케스트레이션
- **참고 문서**: [WeasyPrint 공식 문서](https://doc.courtbouillon.org/weasyprint/stable/)

- **핵심 로직 — 다단계 변환 파이프라인**:

```
Markdown (LLM 생성)
  → _strip_outer_fence()                -- ``` 껍데기 제거
  → _ensure_blank_line_before_tables()  -- 표 앞 빈 줄 강제 삽입
  → markdown.markdown()                 -- Markdown → HTML
  → _classify_wide_tables()             -- <th> 8개+ 표에 class="wide-table" 추가
  → HTML 템플릿 삽입 (CSS에 .wide-table 룰 포함)
  → weasyprint.HTML().write_pdf()       -- HTML → PDF
```

- **핵심 로직 — _classify_wide_tables() (컬럼 수 기반 동적 CSS 분기)**:

CSS는 "컬럼 수가 N개 이상이면" 같은 조건 분기를 지원하지 않습니다. 이 한계를 Python 전처리로 해결합니다:

```python
# src/tools/send_gmail.py
WIDE_TABLE_THRESHOLD = 8

def _classify_wide_tables(html: str) -> str:
    """8개+ 컬럼 표에 class="wide-table"을 부여하여 CSS 축소 대상으로 지정"""
    soup = BeautifulSoup(html, "html.parser")
    for table in soup.find_all("table"):
        first_row = table.find("tr")
        if not first_row:
            continue
        col_count = len(first_row.find_all(["th", "td"]))
        if col_count >= WIDE_TABLE_THRESHOLD:
            existing_classes = table.get("class", [])
            table["class"] = existing_classes + ["wide-table"]
    return str(soup)
```

- **핵심 로직 — 수학적 검증 (A4 물리적 제약)**:

| 상태 | 셀당 최소 폭 계산 | 11컬럼 총 폭 | A4 유효 폭 170mm | 결과 |
|------|-----------------|-------------|-----------------|------|
| **Before** (12pt, 패딩 6px 10px) | 한글 3자 ~12.6mm + 패딩 ~5.3mm = **18mm** | 198mm | 170mm | 28mm 초과 → 잘림 |
| **After** (7.5pt, 패딩 3px 4px) | 한글 3자 ~7.8mm + 패딩 ~2.1mm = **10mm** | 110mm | 170mm | **여유 60mm** |

`table-layout: fixed` 적용 시 170mm / 11 = **15.5mm/컬럼**, 7.5pt 한글 5자(13mm)까지 한 줄 표시 가능.

- **핵심 로직 — 임계값 8의 근거**:

| 테이블 | 컬럼 수 | wide-table 적용? |
|--------|--------|-----------------|
| 시장 환경 스냅샷 | 3 | No |
| SWOT 분석 | 2 | No |
| 연도별 추이표 | 5 | No |
| 요인분석표 | 7 | No |
| **매매 비교표** | **11** | **Yes** |
| **분양 비교표** | **12** | **Yes** |

### 핵심 기능

- **Python + CSS Hybrid 방식**: CSS가 지원하지 않는 "컬럼 수 기반 조건 분기"를 BeautifulSoup DOM 분석으로 해결
- **A4 물리적 제약 대응**: 수학적 검증(셀 폭 x 컬럼 수 vs A4 유효 폭 170mm)으로 최적 폰트/패딩 도출
- **선별적 축소**: 임계값(8컬럼) 기반으로 넓은 표만 축소, 2~7컬럼 표는 원본 유지
- **다단계 전처리 파이프라인**: LLM 출력의 비정형성(코드 펜스, 빈 줄 누락)을 단계별로 정규화

## 12. LLM Multi-Provider Fallback (Gemini 자동 전환)

### 선택 이유

| 기존 방식의 한계 | 해결 필요성 |
|-----------------|------------|
| 모든 분석/보고서 LLM 호출이 **OpenAI 단일 공급자에 의존** — API 장기 장애 시 5회 재시도로도 복구 불가 | 공급자 자체 장애에 대응하려면 **다른 공급자로의 자동 전환(Fallback)** 필요 |
| 재시도(Retry)는 **일시적 에러에만 유효** — Rate Limit, Timeout 등 | 서버 다운, 지역 차단 등 **비일시적 장애**에는 재시도 횟수를 늘려도 해결 불가 |
| 7개 분석 에이전트 + 보고서 에이전트가 동일 공급자 사용 — **단일 장애점(Single Point of Failure)** | 파이프라인 전체가 한 공급자에 종속되지 않는 **회복력(Resilience)** 필요 |

### 구현 방법

- **구현 파일**: `src/utils/llm.py`
  - `RetryableChatGemini` (lines 187~214): Langfuse 추적이 자동 적용된 Gemini LLM 래퍼
  - `_create_gemini_fallback()` (lines 233~252): Gemini fallback 공통 설정 팩토리
  - `LLMProfile.analysis_llm()` (lines 299~321): GPT-5-mini + Gemini-3-flash fallback 체인
  - `LLMProfile.report_llm()` (lines 323~339): GPT-5 + Gemini-3.1-pro fallback 체인

- **핵심 로직 — LangChain `with_fallbacks()` + `__getattr__` 자동 전파**:

```
LLMProfile.analysis_llm() 반환값:
  RetryableChatOpenAI(GPT-5-mini).with_fallbacks([RetryableChatGemini(Gemini-3-flash)])

에이전트에서 llm.bind_tools(tools) 호출 시:
  __getattr__ 프록시가 primary와 fallback 양쪽에 tools를 자동 바인딩
  → 에이전트 코드 변경 없이 동작

실행 시:
  Primary(GPT-5-mini) ──[성공]──→ 결과 반환
       │
       └──[5회 재시도 전부 실패]──→ Fallback(Gemini) ──→ 결과 반환
```

LangChain의 `RunnableWithFallbacks.__getattr__` (`langchain_core/runnables/fallbacks.py:591-645`)이 `bind_tools()`, `with_structured_output()` 호출을 감지하면, primary와 fallback **양쪽 모두에 동일 인자로 자동 전파**합니다. 덕분에 `LLMProfile` 팩토리 한 곳만 수정하면 8개 에이전트 전체에 fallback이 적용됩니다.

- **핵심 로직 — Fallback에서도 Langfuse 비용 추적**:

Primary(OpenAI)는 `RetryableChatOpenAI`가 Langfuse callback을 자동 주입합니다. Fallback(Gemini)도 동일하게 추적하려면 같은 패턴이 필요하므로, `RetryableChatGemini` 래퍼를 만들어 `invoke()` 진입 시 Langfuse callback을 주입합니다. 이를 통해 **어느 쪽이 응답하든 Langfuse 대시보드에서 모델별 비용/토큰을 확인**할 수 있습니다.

- **참고 문서**:
  - [LangChain Fallbacks](https://python.langchain.com/docs/how_to/fallbacks/)
  - [Gemini API 공식 문서](https://ai.google.dev/gemini-api/docs)

### Fallback 모델 매핑

| 용도 | Primary | Fallback | max_tokens |
|------|---------|----------|------------|
| 분석 에이전트 (7개) | GPT-5-mini | gemini-3-flash-preview | 65,536 |
| 보고서 에이전트 | GPT-5 | gemini-3.1-pro-preview | 65,536 |

### 핵심 기능

- **에이전트 코드 변경 0**: `__getattr__` 자동 전파로 `bind_tools()`, `with_structured_output()` 모두 primary/fallback에 동시 적용
- **공급자 자동 전환**: Primary 5회 재시도 전부 실패 시 Gemini fallback으로 즉시 전환
- **Fallback Langfuse 추적**: `RetryableChatGemini` 래퍼로 fallback 호출도 비용/토큰 추적 보장
- **중앙 집중 관리**: `LLMProfile` 팩토리 함수 한 곳에서 primary/fallback 쌍을 관리
